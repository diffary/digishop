# DigiShop — дизайн-документ

Дата: 2026-08-12
Статус: утверждён пользователем, прошёл спек-ревью, готов к планированию

## 1. Что это

DigiShop — магазин цифровых товаров (демо-товары: наборы игровых ассетов/пресетов). Двойная цель:

1. **Портфолио**: закрыть пробелы резюме — multi-service Docker, Celery, Redis, платёжный флоу, полноценный React-фронт, managed-деплой.
2. **Потенциальный реальный запуск**: архитектура готова к реальным товарам и реальному платёжному провайдеру (LiqPay) без переписывания.

Срок: ~2–3 недели активной работы. Код в основном генерирует AI-ассистент; пользователь читает и учится по сопровождающим Obsidian-заметкам (см. §9).

### Пользовательский флоу MVP

1. Гость видит каталог товаров с категориями и поиском.
2. Регистрация/вход: email+пароль **или** Google OAuth2.
3. Корзина → оформление заказа → редирект на Stripe Checkout (test mode).
4. Stripe шлёт вебхук → заказ помечается оплаченным → Celery-задача генерирует ссылки на скачивание и «отправляет письмо».
5. Личный кабинет: история заказов, кнопки скачивания купленных файлов.

### Не входит в MVP (этап 2, по остатку времени)

Возвраты, промокоды, отзывы, второй OAuth-провайдер, реальная отправка email (Resend), S3-хранилище файлов. Админ-панели в MVP нет — товары заводятся seed-скриптом/через API.

**Этап 2, пункт первый — Django-админка** (~2–4 дня, по явному запросу пользователя — закрыть пробел «Django» в резюме): отдельный сервис-«бэк-офис» на Django поверх той же PostgreSQL — готовая админка для товаров, категорий и просмотра заказов. Владелец схемы — Alembic; Django-модели описываются с `managed=False` (читают таблицы, миграциями не управляют). В docker-compose добавляется шестым сервисом, на Render — отдельным free-сервисом (админке можно «спать»). Публичный API остаётся на FastAPI; связка «FastAPI для публичного API + Django для бэк-офиса» — реальный продакшн-паттерн и сильный ответ на собеседовании.

## 2. Архитектура и хостинг (строго бесплатно)

| Компонент | Где живёт | Тариф |
|---|---|---|
| React SPA | Vercel | free |
| FastAPI + Celery worker (+beat через `-B`) | Render, один контейнер | free (засыпает; анти-сон пинг) |
| PostgreSQL | Neon | free |
| Redis | Upstash | free |
| Платежи | Stripe test mode | free |
| Ошибки | Sentry | free |

Один контейнер на Render — осознанный компромисс бесплатного тарифа: отдельный воркер там платный, поэтому стартовый скрипт поднимает uvicorn и Celery-воркер вместе. **Эталонная архитектура — docker-compose на 5 сервисов (api, worker, beat, postgres, redis) — остаётся в репозитории** для локальной разработки и CI; в резюме идёт именно она.

Анти-сон: GitHub Actions по крону раз в 10 минут дёргает `/health` (заодно бесплатный мониторинг доступности).

Upstash-нюанс: Celery настраивается на редкий опрос очереди (`broker_transport_options`), иначе постоянный polling сжигает бесплатный лимит команд.

## 3. Модель данных (PostgreSQL, SQLAlchemy async, Alembic)

- **User**: id, email, password_hash (nullable — у Google-пользователей пароля нет), google_id (nullable, unique), created_at.
- **Category**: id, name, slug.
- **Product**: id, category_id, name, slug, description, price (integer, центы — деньги никогда не float), image_url, file_key, is_active.
- **Order**: id, user_id, status, total, provider (`stripe`), payment_session_id, created_at. Имена колонок провайдеро-независимые — чтобы LiqPay лёг в ту же схему. Статусная машина: `pending → paid → delivered`, `pending → failed`. Переходы только по разрешённой схеме.
- **OrderItem**: order_id, product_id, price_at_purchase (цена фиксируется на момент покупки).
- **DownloadLink**: order_item_id, token (uuid), expires_at, download_count. Скачивание только по временной токен-ссылке; download_count — информационный счётчик (жёсткого лимита скачиваний в MVP нет).
- **Notification**: id, user_id, order_id, type, payload (json), created_at — сюда `deliver_order` пишет «отправленные письма» в MVP; при подключении реальной почты (этап 2) таблица становится логом отправки.

Корзина в БД не хранится — живёт на фронте (Zustand + localStorage). Сервер видит корзину в момент `POST /orders`, где перевалидирует цены по БД.

## 4. Структура бэкенда

```
backend/
  app/
    api/          # роутеры: auth, products, orders, downloads, webhooks
    core/         # конфиг (pydantic-settings), security (JWT), зависимости
    models/       # SQLAlchemy-модели
    schemas/      # Pydantic v2
    services/     # бизнес-логика: orders, delivery, catalog
    payments/     # base.py (интерфейс PaymentProvider) + stripe.py
    storage/      # base.py (интерфейс Storage) + local.py
    tasks/        # celery_app.py, delivery.py, maintenance.py
  tests/
  alembic/
```

Ключевые абстракции:

- **PaymentProvider** (`create_checkout`, `verify_webhook`): Stripe сегодня, LiqPay добавляется реализацией интерфейса, без правки логики заказов.
- **Storage** (`get_file`, `exists`): в MVP файлы демо-товаров лежат локально в контейнере; замена на S3-совместимое хранилище — реализация интерфейса.

## 5. Auth

- Email+пароль: bcrypt-хэш, JWT (access-токен) в заголовке Authorization.
- **Куки не используются** (кроме временной state-куки authlib во время OAuth-редиректа): фронт и API на разных доменах (vercel.app / onrender.com), кросс-доменные httpOnly-куки хрупки (SameSite/third-party-блокировки), поэтому токен хранится в localStorage и передаётся заголовком. Трекинговых кук нет → cookie-баннер (GDPR) не нужен.
- **Google OAuth2** через authlib: редирект-флоу, по callback создаём/находим User по google_id/email. Передача JWT в SPA после кросс-доменного редиректа — через **одноразовый код**: callback кладёт JWT в Redis под коротким кодом (TTL 60 сек) и редиректит на фронт с `?code=...`; SPA обменивает код на JWT запросом `POST /auth/exchange` (код одноразовый — удаляется при обмене). Токен не светится в URL/истории браузера — и это ещё одно применение Redis. Один OAuth-провайдер в MVP — второй ничему новому не учит.
- Rate limiting на `/auth/login` и `/auth/register` через Redis (защита от перебора).

## 6. Платёжный флоу, Celery, Redis

### Оплата

1. `POST /orders`: бэкенд перевалидирует цены по БД (ценам с фронта не доверяем), создаёт Order `pending`, создаёт Stripe Checkout Session, возвращает URL.
2. Пользователь платит тестовой картой на странице Stripe.
3. `POST /webhooks/stripe` (`checkout.session.completed`):
   - проверка подписи вебхука;
   - идемпотентность: обрабатывается только переход `pending → paid`, повторный вебхук — no-op;
   - быстрый ответ: обработчик меняет статус, ставит Celery-задачу и сразу отвечает 200.

### Celery-задачи

- `deliver_order(order_id)`: генерирует DownloadLink'и, «отправляет письмо» (MVP: запись в таблицу Notification + лог), переводит заказ в `delivered`. Retry с экспоненциальной задержкой, max 5 попыток; после исчерпания заказ остаётся `paid` с флагом ошибки в логах/Sentry.
- `expire_pending_orders()` (beat, периодическая): `pending` старше 1 часа → `failed`.
- `cleanup_expired_links()` (beat): удаляет DownloadLink с истёкшим `expires_at` (эндпоинт скачивания и сам отвергает протухший токен — задача лишь чистит мусор).

### Redis (Upstash) — три роли

1. Брокер Celery (с настроенным редким опросом — см. §2).
2. Кэш каталога: список товаров и карточки, TTL ~5 минут, инвалидация при изменении товара.
3. Rate limiting для auth-эндпоинтов.

## 7. Фронтенд (React 18 + TS + Vite)

- Страницы: каталог (фильтр по категории, поиск), карточка товара, корзина, логин/регистрация (+кнопка Google), результат заказа, личный кабинет (заказы, скачивания).
- Состояние: Zustand (корзина + auth-токен, персист в localStorage), TanStack Query (все запросы к API).
- Стили: Tailwind.
- API-клиент: обёртка над fetch — подстановка JWT, обработка 401 (разлогин).

## 8. Тесты, CI, обработка ошибок

### Тесты (pytest, цель ~70%+ покрытия бэкенда)

- API-тесты через httpx AsyncClient: auth (оба способа), каталог, создание заказа с перевалидацией цен.
- **Приоритетные тесты — вебхук**: валидная/невалидная подпись, повторный вебхук не доставляет дважды, вебхук по несуществующему заказу.
- Celery в eager-режиме; Stripe и Google мокаются — тесты не ходят в сеть.
- Фронт: Vitest, несколько компонентных тестов корзины.

### CI (GitHub Actions)

На каждый пуш: ruff + pytest + сборка docker-образа; фронт: tsc + vitest + build. Деплой: Vercel и Render автоматически подхватывают пуш в `main`. Отдельный workflow — крон-пинг `/health`.

### Ошибки

- Единый формат ошибок API + глобальный exception handler.
- Sentry (free) для бэка и фронта.
- Локальная разработка вебхуков — через Stripe CLI (`stripe listen --forward-to ...`).

По ходу разработки ведутся заметки в `D:\разное\обсидиан\халаль\` — **плоско, без подпапок**, имена вида `DigiShop — <тема>.md`. Формат каждой: Что это → Зачем именно здесь → Как устроено у нас (ссылки на файлы) → Альтернативы и почему не они → Вопросы с собеседования с ответами.

Обязательные темы: карта проекта, Celery, Stripe-вебхуки и идемпотентность, Redis (кэш/инвалидация/rate limit), OAuth2, JWT, статусная машина заказа, Alembic, деплой на free-tier.

## 10. Критерии готовности MVP

1. Полный флоу «каталог → корзина → Stripe test → скачивание файла» работает на проде (Vercel+Render).
2. `docker compose up` локально поднимает все 5 сервисов, флоу работает end-to-end.
3. CI зелёный, покрытие бэкенда ~70%+.
4. Google-вход работает на проде.
5. Obsidian-заметки написаны по всем обязательным темам §9.
