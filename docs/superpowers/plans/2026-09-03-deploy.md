**Goal:** Живой прод на строго бесплатных тарифах: React SPA на Vercel, FastAPI + Celery worker (+beat через `-B`) в ОДНОМ контейнере на Render free, PostgreSQL на Neon free, Redis на Upstash free, Stripe test mode. ## Предпосылки и ключевые решения

**Сверенные факты кода** (проверено по файлам, не по памяти):

- Env-переменные бэкенда (`backend/app/core/config.py`): `DATABASE_URL`, `REDIS_URL`, `JWT_SECRET` (min 16 символов), `JWT_ALGORITHM`, `JWT_EXPIRE_MINUTES`, `STRIPE_SECRET_KEY`, `STRIPE_WEBHOOK_SECRET`, `FRONTEND_URL`, `BACKEND_URL`, `GOOGLE_CLIENT_ID`, `GOOGLE_CLIENT_SECRET`. `backend/.env.example` совпадает.
- CORS (`backend/app/main.py:39`): `allow_origins=[get_settings().frontend_url]` — ровно один origin.
- `/health` уже существует (`backend/app/api/health.py`) — эндпоинт для пинга и Render health check есть, создавать не надо.
- `backend/Dockerfile` CMD жёстко биндит порт 8000; Render передаёт свой порт через env `PORT` → нужен запуск с `${PORT:-8000}`.
- Celery (`backend/app/tasks/celery_app.py`): `result_backend=None`, `task_ignore_result=True`, `broker_transport_options={"health_check_interval": 120}`; beat-расписание: `expire-pending-orders` каждые 15 мин, `check-undelivered-paid` каждые 10 мин, `cleanup-expired-links` раз в сутки. Порог протухания pending — 75 мин (`PENDING_TTL_HOURS=1` + `PENDING_EXPIRY_GRACE_MINUTES=15` в `backend/app/services/maintenance.py`).
- Файлы товаров запечены в образ: `COPY . .` в Dockerfile кладёт `backend/files/demo.zip`; `.dockerignore` исключает только `.venv/`, `__pycache__/`, кэши, `tests/`, `.env`. `LocalStorage` резолвит `file_key` вида `files/demo.zip` от корня `/app` — в контейнере Render скачивание работает без S3.
- Миграции/сид: `alembic/env.py` берёт URL из `get_settings().database_url` (тот же async-движок); сид идемпотентный — `uv run python -m scripts.seed` (skip-if-exists). Автоматического запуска миграций сейчас нет нигде — добавляется в `start.sh`.

- `backend/app/core/rate_limit.py:18-20` содержит явный комментарий «в плане 4 добавится учёт X-Forwarded-For» — закрывается флагами uvicorn (Решение 6).
- Sentry в коде НЕ подключён (ни в `backend/pyproject.toml`, ни в `frontend/package.json`) — в этот план не входит, отдельный мини-этап.

**Решение 1 — один контейнер на Render: `backend/start.sh`, запуск через Docker Command.** Скрипт: `alembic upgrade head` → `python -m scripts.seed` (идемпотентен; известный долг «не обновляет существующие записи» не мешает) → celery worker с встроенным beat (`-B`) и uvicorn как два фоновых процесса + `wait -n; exit 1` — смерть любого из двух валит контейнер, Render его перезапускает (иначе воркер умирал бы молча, а «monitoring» `check_undelivered_paid` умирал бы вместе с ним). Dockerfile НЕ меняется: локально и в CI образ ведёт себя как раньше, а на Render в настройках сервиса задаётся Docker Command `bash ./start.sh` (запуск через `bash` — заодно снимает проблему exec-бита у файла, созданного на Windows).

**Решение 2 — beat внутри того же контейнера (`-B`), не внешний cron.** Обоснование: (а) спека §2 прямо фиксирует «+beat через `-B`»; (б) Render Cron Jobs — платные, а GitHub Actions cron потребовал бы нового HTTP-эндпоинта «дёрни maintenance» с отдельной авторизацией — лишний код и поверхность атаки; (в) инстанс один, значит второй beat не появится (single-beat инвариант соблюдён). Файл расписания beat уводим в `/tmp` (`-s /tmp/celerybeat-schedule`) — ФС Render эфемерна, состояние beat и не должно переживать рестарт.

**Решение 3 — бюджет команд Upstash и редкий опрос брокера.** Сверено с установленным kombu 5.6.2: transport option `polling_interval` прокидывается в `brpop_timeout` (`kombu/transport/virtual/base.py:944-946` → `kombu/transport/redis.py:1351-1353`), по умолчанию BRPOP-таймаут = 1 сек → простаивающий воркер сжёг бы ~2.6 млн команд/мес. Ставим `broker_transport_options={"health_check_interval": 120, "polling_interval": 15}`. Оценка при 15 сек: BRPOP ≈ 173k/мес + health-check PING ≈ 22k + beat-отправки (4/ч + 6/ч + 1/сут ≈ 7.3k задач/мес, по нескольку команд на LPUSH/ack) ≈ 25k + приложение (кэш каталога, rate limit, oauth-коды — демо-трафик) < 10k ⇒ **≈ 230k/мес при лимите free-тарифа Upstash 500k команд/мес** — двукратный запас. Контроль: через сутки после деплоя посмотреть Usage в дашборде Upstash; если фактический лимит аккаунта окажется суточным/меньшим — поднять `polling_interval` до 30 (срезает BRPOP вдвое; латентность старта задачи ≤ 30 сек некритична: доставка заказа и так асинхронная).

**Решение 4 — admin_panel НЕ деплоим, остаётся локальным.** Арифметика free-тарифа Render: 750 инстанс-часов/мес на воркспейс, анти-сон держит API бодрствующим ~744 ч в 31-дневном месяце — второй сервис (даже «спящая» админка, разбуженная на пару часов) выедает остаток и рискует суспендом API до конца месяца. Дешёвое приемлемое решение: админка живёт в docker compose; для правки ПРОД-товаров пользователь локально запускает `admin` с `DATABASE_URL` от Neon (sync-формат `postgresql://...?sslmode=require` — парсер `admin_panel/config/db_url.py` понимает `sslmode` по плану админки) — **[РУЧНОЙ ШАГ ПОЛЬЗОВАТЕЛЯ]**, секрет только в локальном окружении. Фиксируется в README.

**Решение 5 — CORS: комма-список нужен, но `FRONTEND_URL` остаётся одиночным.** `frontend_url` используется не только для CORS, но и для построения redirect'ов (`oauth.py:79`, `stripe_provider.py:33-34`) — списком быть не может. Добавляем отдельный опциональный `CORS_EXTRA_ORIGINS` (comma-separated, по умолчанию пусто): прод-origin Vercel задаётся через `FRONTEND_URL`, а extra — для локального фронта против прод-API и Vercel preview-доменов при надобности. Дефолт сохраняет текущее поведение. ВАЖНО в раннбуке: origin сравнивается точно — `FRONTEND_URL` без завершающего `/`.

**Решение 6 — прокси-заголовки Render:** uvicorn запускается с `--proxy-headers --forwarded-allow-ips "*"` — `request.client.host` начинает отражать реальный IP из `X-Forwarded-For`, rate limit перестаёт складывать всех пользователей в один бакет (закрывает комментарий-обещание в `rate_limit.py`). Код rate limit не меняется.

**Решение 7 — анти-сон: GitHub Actions cron `*/10` + репозиторий ПУБЛИЧНЫЙ.** Минимальный интервал GH cron — 5 мин, фактические запуски дрожат на минуты. Критично: в приватном репо пинг каждые 10 мин ≈ 4 320 тарифицируемых минут/мес > 2 000 бесплатных; в публичном Actions-минуты не тарифицируются — репо и так портфолио, делаем публичным **[РУЧНОЙ ШАГ ПОЛЬЗОВАТЕЛЯ]** (перед этим убедиться, что в истории git нет секретов; `.env` в git не попадал — в `.gitignore`/`.dockerignore`). Известные оговорки зафиксировать в README: scheduled-workflow автоматически отключается после 60 дней без активности в репо (включить вручную кнопкой); если Render-метрики покажут засыпания из-за джиттера крона — ужать до `*/5`; `curl --retry` с большим `--max-time` заодно будит сервис после холодного старта (~50 сек).

**Решение 8 — строки подключения (формат сверен с кодом):**
- Neon выдаёт `postgresql://...?sslmode=require&channel_binding=require`. Для нас: схема → `postgresql+asyncpg://`, параметры → **только** `?ssl=require` (диалект SQLAlchemy передаёт query verbatim в `asyncpg.connect` — `opts.update(url.query)` в `sqlalchemy/dialects/postgresql/asyncpg.py:1137`; `sslmode`/`channel_binding` asyncpg-кваргами не являются и уронят коннект). Брать **unpooled**-строку (без `-pooler`): asyncpg использует prepared statements, транзакционный pgbouncer Neon с ними конфликтует; масштаб демо прямые коннекты держит.
- Upstash выдаёт `rediss://...`. Celery для `rediss://` требует явного `ssl_cert_reqs` → к URL дописать `?ssl_cert_reqs=required`; redis-py (`Redis.from_url` в `app/core/redis.py:13`) этот query-параметр тоже понимает — одна переменная `REDIS_URL` обслуживает и брокер, и кэш/rate-limit.

## Rollback

Всё на free-tier — необратимых состояний нет: Render и Vercel держат историю деплоев с кнопкой Rollback/Redeploy предыдущей сборки; код откатывается revert-коммитом в `main` (автодеплой подхватит). Миграции аддитивные, `start.sh` прогоняет `alembic upgrade head` на каждом старте — откат схемы через `alembic downgrade` вручную, у Neon free есть point-in-time restore на короткое окно. Худший случай — снести и пересоздать ресурсы Neon/Upstash/Render/Vercel по раннбуку Task 3: миграции и сид накатятся сами при первом старте, вручную восстанавливаются только env-значения (у пользователя) и webhook/redirect-URI в Stripe/Google.

## Критерий завершения плана

1. Живой URL работает end-to-end: регистрация → покупка картой 4242 → заказ `delivered` → файл скачан; Google-вход работает (критерии MVP §10 п.1, п.4).
2. Stripe webhook на проде доставляется с 200 без CLI-туннеля; аккаунт Stripe остаётся в test mode.
3. Анти-сон: пинг-workflow зелёный ≥ суток, Render не показывает засыпаний; расход Upstash в экстраполяции месяца внутри бесплатного лимита.
4. Локальная эталонная архитектура не деградировала: `docker compose up` поднимает 6 сервисов как раньше, CI (3 джоба) зелёный.
5. README содержит раздел Deploy (env-таблица, раннбук, анти-сон, решение по админке); прод-секреты нигде в репо не фигурируют.
6. Ссылка на живой прод добавлена в резюме/CV пользователя.
